Step5. 바이브코딩으로 내 앱 확장하기

Step4까지 완성해 배포한 급식알리미를 AI 코딩 도구와 함께 확장한다. 이제부터는 문법을 하나하나 직접 치는 대신, AI에게 정확하게 요청하고 결과를 검증하는 방식으로 개발한다.

01바이브코딩이란 무엇인가

지금까지는 원하는 기능을 머릿속으로 그리고, 문법 하나하나를 직접 코드로 옮겼다. 바이브코딩은 원하는 결과를 AI에게 구체적인 말로 설명하고, AI가 만들어준 코드를 이해하고 검증하며 적용하는 개발 방식이다. 타이핑을 줄여주는 게 아니라, "정확하게 요청하는 능력"이 새로운 핵심 역량이 된다는 점이 다르다.
나
프롬프트 작성
→구체적인 요청
AI
코드 생성
→실행·확인
나
이해·검증·적용
Step1과 같은 원리
Step1에서 본 API의 요청-응답 구조와 닮았다. 모호한 요청을 보내면 모호한 응답이 오듯, 프롬프트가 구체적이지 않으면 AI도 내가 원하는 것과 다른 코드를 준다.

02실습 준비

  1. 사용할 AI 코딩 도구(Cursor, Claude, ChatGPT 등)에 로그인되어 있는지 확인한다.
  2. Step4까지 작업한 프로젝트 폴더가 VS Code에 열려 있고, GitHub 저장소와 연결된 상태인지 확인한다.
  3. 터미널에서 streamlit run app.py로 지금 앱이 정상 실행되는지 다시 확인한다 — 여기서부터는 이 상태를 기준으로 기능을 하나씩 추가한다.

03좋은 프롬프트 vs 나쁜 프롬프트

AI는 내가 말한 만큼만 이해한다. 같은 목표라도 프롬프트에 따라 결과가 크게 달라진다.

나쁨 ✗
"학교 이름 즐겨찾기 기능 좀 만들어줘. 디자인도 예쁘게 해주고, 에러도 안 나게 고쳐줘."
좋음 ✓
"지금 app.py의 school_name 입력창 위에, st.session_state를 이용한 즐겨찾기 기능을 추가해줘. 즐겨찾기한 학교 이름을 사이드바에 버튼 목록으로 보여주고, 버튼을 클릭하면 입력창에 그 이름이 자동으로 채워지게 해줘."

나쁜 프롬프트는 "예쁘게", "에러 없이"처럼 기준이 없고, 즐겨찾기·디자인·에러 수정을 한 번에 요청한다. 좋은 프롬프트는 어떤 파일의 어느 부분에, 어떤 동작을 원하는지 구체적으로 그려준다.

04지켜야 할 두 가지 원칙

원칙 1 · 원인부터 물어보기
에러가 나면 "고쳐줘" 대신 "이 에러가 왜 났는지 먼저 설명해줘"라고 요청한다. 원인을 이해해야 다음에 비슷한 에러를 스스로 해결할 수 있다.
원칙 2 · 한 번에 하나씩
기능을 여러 개 한꺼번에 요청하지 않는다. 하나를 완성하고 streamlit run app.py로 실행해 확인한 뒤, 다음 요청으로 넘어간다.

05실습① 즐겨찾기 기능 추가

Step3에서 완성한 school_name = st.text_input(...) 부분에 즐겨찾기를 연결한다.

AI에게 보낼 프롬프트
"지금 app.py의 school_name 입력창 위에, st.session_state를 이용한 즐겨찾기 기능을 추가해줘. 사이드바에 즐겨찾기한 학교 이름을 버튼 목록으로 보여주고, 버튼을 클릭하면 school_name 입력창에 그 이름이 자동으로 채워지게 해줘. 입력창 옆에는 현재 입력된 이름을 즐겨찾기에 추가하는 버튼도 만들어줘."

07실습③ 에러가 나면 원인부터

주말이나 방학처럼 급식이 없는 날짜를 조회해본다.

주말 날짜로 조회하면(터미널)
Traceback (most recent call last):
  File "app.py", line 24, in get_meal
    return data["mealServiceDietInfo"][1]["row"][0]["DDISH_NM"]
IndexError: list index out of range

Step2에서 본 것처럼 나이스 API 응답은 [head, row] 구조다. 급식이 없는 날은 row 자체가 통째로 빠진 채 head만 돌아오기 때문에, 리스트에 [1] 인덱스가 존재하지 않는다.

AI에게 보낼 프롬프트 (①원칙 적용)
"get_meal 함수에서 주말 날짜를 조회하면 'IndexError: list index out of range' 에러가 나. 이 에러가 왜 발생하는지 원인을 먼저 설명해주고, 급식이 없는 날에는 에러 대신 None을 반환하도록 고쳐줘."
app.py — 수정된 get_meal()
def get_meal(office_code, school_code, date):
    url = "https://open.neis.go.kr/hub/mealServiceDietInfo"
    params = {
        "KEY": API_KEY, "Type": "json",
        "pIndex": 1, "pSize": 5,
        "ATPT_OFCDC_SC_CODE": office_code,
        "SD_SCHUL_CODE": school_code,
        "MLSV_YMD": date
    }
    data = requests.get(url, params=params).json()
    if len(data["mealServiceDietInfo"]) < 2:
        return None
    return data["mealServiceDietInfo"][1]["row"][0]["DDISH_NM"]

이해하고 넘어가기
get_meal()이 None을 반환하면, Step3에서 이미 만들어둔 if raw_menu: ... else: st.error(...) 분기가 그대로 작동해서 자연스럽게 안내 메시지가 뜬다. 새 코드를 추가하지 않고도, 이전에 짠 코드 구조 덕분에 문제가 해결됐다.

08실습④ 여러 날짜 한 번에 보기 — 무거워지는 앱

지금은 하루치 급식만 조회한다. 이번엔 이번 주(월~금) 급식을 한 번에 비교해서 보여주는 기능을 추가한다. 이 기능부터는 API를 여러 번 호출해야 해서, 캐싱이 왜 필요한지 직접 느껴볼 수 있다.

AI에게 보낼 프롬프트
"app.py에 '이번 주 급식 보기' 버튼을 추가해줘. 누르면 선택한 날짜가 속한 주의 월요일부터 금요일까지 날짜를 계산해서, 각 날짜의 급식을 get_meal 함수로 순서대로 조회하고, st.columns로 요일별로 나란히 보여줘."
app.py — AI가 제안한 코드
import datetime

def get_week_dates(date):
    monday = date - datetime.timedelta(days=date.weekday())
    return [monday + datetime.timedelta(days=i) for i in range(5)]

if st.button("이번 주 급식 보기"):
    school_code = find_school(office_code, school_name)
    week_dates = get_week_dates(date)

    cols = st.columns(5)
    for col, d in zip(cols, week_dates):
        with col:
            st.write(f"**{d.strftime('%m/%d')} ({'월화수목금'[d.weekday()]})**")
            with st.spinner("불러오는 중..."):
                raw = get_meal(office_code, school_code, d.strftime("%Y%m%d"))
            if raw:
                for dish in clean_menu(raw):
                    st.caption(dish)

09실습⑤ 캐싱으로 성능 개선하기

Step2 끝에서 미뤄뒀던 이야기다 — "매번 검색하는 건 비효율적이지만, 캐싱은 Streamlit에 익숙해진 뒤 다룬다"고 했던 바로 그 부분을 지금 AI와 함께 해결한다.

AI에게 보낼 프롬프트
"find_school 함수랑 get_meal 함수에 캐싱을 추가해줘. 같은 학교 이름이나 같은 날짜로 다시 조회할 때는 API를 다시 부르지 않고 저장해둔 결과를 바로 보여주면 좋겠어."
app.py — 함수 정의 위에 한 줄씩 추가
@st.cache_data
def find_school(office_code, school_name):
    ...

@st.cache_data
def get_meal(office_code, school_code, date):
    ...
이해하고 넘어가기
@st.cache_data는 함수를 실행하기 전에 같은 인자로 이미 실행한 적이 있는지 먼저 확인한다. 있다면 함수를 다시 실행하지 않고 저장해둔 결과를 그대로 돌려준다. Step3에서 위젯 값이 바뀔 때마다 스크립트 전체가 다시 실행된다고 배웠는데, 캐싱된 함수만큼은 인자가 같으면 그 재실행 안에서도 실제 호출을 건너뛴다.
캐싱 전캐싱 후
같은 학교 재조회find_school API 재호출저장된 학교 코드 즉시 사용
같은 주 재조회get_meal 5번 재호출저장된 급식 데이터 즉시 사용
체감 속도누를 때마다 로딩첫 조회만 로딩, 이후 즉시
직접 확인하기 — 캐싱을 추가한 뒤 같은 학교·같은 주를 다시 조회해본다. 처음 조회할 때만 st.spinner가 잠깐 보이고, 두 번째부터는 스피너 없이 바로 결과가 뜨면 캐싱이 정상 동작하는 것이다.
참고 — 캐시가 오래된 값을 보여준다면
@st.cache_data는 기본적으로 앱이 재시작되기 전까지 결과를 계속 저장해둔다. 급식 메뉴가 실제로 바뀌었는데 예전 값이 보인다면, 화면 오른쪽 위 메뉴에서 Clear cache를 누르거나, @st.cache_data(ttl=3600)처럼 유효 시간(초)을 정해줄 수 있다.

10실습⑥ 설명 요청 — AI가 준 코드 이해하기

지금까지는 AI가 준 코드를 실행만 해봤다. 이번에는 05번에서 만든 즐겨찾기 코드 중 for fav in st.session_state.favorites:와 그 안의 if st.button(fav): 부분이 정확히 언제, 어떤 순서로 실행되는지 AI에게 설명을 요청해본다.

AI에게 보낼 프롬프트
"방금 만든 즐겨찾기 코드에서 for fav in st.session_state.favorites: 부분과 그 안의 if st.button(fav): 부분이 정확히 어떤 순서로, 언제 실행되는지 한 줄씩 설명해줘. 예시를 들어서 설명해줘."
AI의 설명 (요약)
1. 사이드바가 그려질 때, 저장된 즐겨찾기 이름 개수만큼 버튼이 하나씩 만들어진다.
2. 사용자가 버튼 중 하나를 클릭하면, Streamlit은 위젯 값이 바뀐 것으로 보고
   스크립트 전체를 처음부터 다시 실행한다 (Step3 01번 참고).
3. 다시 실행되는 동안 st.session_state.selected_school 값이 방금 클릭한
   학교 이름으로 바뀌어 있어서, 그 아래 text_input의 기본값이 그 이름으로 채워진다.
재사용 가능한 질문 패턴
코드를 이해할 때 아래 세 가지 질문은 어떤 코드에나 그대로 써먹을 수 있다.
  • "이 줄이 정확히 뭘 하는 거야?"
  • "이 코드가 실행되는 순서를 예시를 들어서 설명해줘"
  • "이 옵션(파라미터)을 빼면 어떻게 달라져?"
직접 해보기 — 06번의 zip(cols, menu) 줄을 골라 같은 방식으로 AI에게 설명을 요청해보고, 이해한 내용을 짝에게 AI의 설명을 보지 않고 자기 말로 설명해본다.

찾아보기 — 이 코드의 문제는?
AI는 "일단 실행되는 코드"를 최우선으로 만들기 때문에, Step4에서 st.secrets로 분리했던 인증키를 다시 코드에 그대로 적어서 줄 때가 있다. 이 코드를 그대로 GitHub에 Commit하면 인증키가 다시 공개된다. AI가 준 코드라도 Step4의 규칙(인증키는 코드에 적지 않는다)이 지켜졌는지는 내가 직접 확인해야 한다.

이 외에도 AI와 작업할 때 스스로 점검해야 할 것들이 있다.

할루시네이션AI는 존재하지 않는 함수나 틀린 설명도 자신 있게 말할 수 있다. 설명을 들었다고 끝내지 말고, 실행해서 직접 결과를 확인한다.
보안인증키·개인정보가 코드에 그대로 남아있지 않은지 Commit 전에 한 번 더 확인한다.
저작권AI가 제안한 코드 조각이 특정 오픈소스 프로젝트를 그대로 가져온 것일 수 있다. 공개 저장소에 올릴 코드라면 라이선스 문제가 없는지 확인한다.
  1. 인증키·비밀번호가 코드에 그대로 적혀 있지 않은가 (st.secrets를 쓰고 있는가)
  2. 실행해봤을 때 AI의 설명대로 실제로 동작하는가
  3. 처음 보는 라이브러리를 쓴다면, 정말 설치돼 있는지 pip list로 확인했는가
  4. 공개 저장소에 올릴 코드라면, 가져온 코드 조각에 라이선스 문제가 없는가

13자주 만나는 오류

모르는 함수/라이브러리가 섞인 코드를 줌실행해서 에러 메시지를 확인한 뒤, "이 라이브러리가 설치돼 있어야 하는지, pip install이 필요한지 알려줘"라고 되묻는다.
코드를 통째로 바꿔서 기존 기능이 사라짐04번 "한 번에 하나씩" 원칙 위반. 직전 버전으로 되돌리고, 더 작은 단위로 다시 요청한다.
session_state 관련 오류위젯의 key와 session_state 키 이름이 겹칠 때 자주 발생한다. AI에게 "이 키 이름이 왜 충돌하는지" 설명을 요청한다.
고친 코드가 배포된 앱에 반영 안 됨로컬에서만 수정하고 GitHub에는 다시 올리지 않은 경우다. Step4의 05~06번대로 변경된 app.py를 다시 Commit한다.
캐싱했더니 예전 급식이 계속 보임09번 참고 — 오른쪽 위 메뉴의 Clear cache를 누르거나, @st.cache_data(ttl=...)로 유효 시간을 정해준다.

정리

  • AI에게는 "어느 파일의 어느 부분에, 무엇을" 원하는지 구체적으로 설명해야 원하는 코드를 받는다.
  • 에러가 나면 고쳐달라고 하기 전에 원인부터 물어본다.
  • 기능은 한 번에 하나씩 요청하고, 매번 실행해서 확인한다.
  • 같은 입력에 같은 API를 반복 호출하는 부분은 @st.cache_data로 캐싱해 속도와 서버 부담을 함께 줄인다.
  • 이해 안 되는 코드는 "이 줄이 뭘 하는 거야?"라고 되물어서 내 말로 설명할 수 있을 때까지 확인한다.
  • AI가 준 코드라도 결국 내가 이해하고 책임지는 내 코드다 — 특히 인증키가 그대로 남아있지 않은지는 Commit 전에 직접 확인한다.
여기까지 — 급식알리미가 완성됐다. Step4에서 받은 streamlit.app 배포 링크를 다시 확인하고, 오늘 무엇을 만들고 무엇을 배웠는지 짧게 발표를 준비하며 마무리한다. 수고했다!
